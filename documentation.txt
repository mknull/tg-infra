it-jobs — System Documentation
================================

Overview
--------

An automated job-hunting pipeline that monitors two Telegram job groups and a research
mailing list, filters postings with a two-stage LLM triage, and delivers matches to a
personal Telegram chat. Runs unattended as a systemd user service every two hours.

No Claude Code, no Anthropic SDK, no heavyweight dependencies. The entire stack is Python
stdlib plus Telethon, talking directly to three REST APIs.


What it does
------------

Every two hours, three scripts run in sequence:

1. it-jobs-poller.py   — reads new posts from two Telegram job groups using a Telethon
                         user-API session, writes each post as a JSON file to a local
                         message queue.

2. it-jobs-triage.py  — reads the queue, puts each post through a two-stage DeepSeek
                         filter, and sends matches to a Telegram bot.

3. email-triage.py    — fetches new emails from an Outlook inbox via the Microsoft Graph
                         API, puts each through the same two-stage filter, and sends
                         matches to the same bot.


Architecture
------------

Telegram group pipeline:

    Telethon (user API)
        |
        v
    it-jobs-poller.py
        |  writes JSON to ~/.it-jobs/message_queue/
        v
    it-jobs-triage.py
        |  Flash -> Pro
        v
    Telegram Bot API -> personal chat

The poller handles two channels — @it_jobs_cyprus and @cyithr — in a single Telethon
session. Each channel has its own cursor file (an integer message ID) so the poller always
picks up exactly where it left off. Posts are written as self-contained JSON files with the
full text and metadata (channel, sender, timestamp).

The triage script reads every file in the queue and routes it by channel. Both channels
share the same Pro model for full evaluation, but use different Flash strategies (see
below).

Email pipeline:

    Microsoft Graph API
        |
        v
    email-triage.py  (poll + triage combined)
        |  Flash -> Pro
        v
    Telegram Bot API -> personal chat

Email is a single combined script because body fetching happens mid-triage: Flash sees only
the From address and Subject line first, and only if it decides to read further does the
script fetch the full body. Separating poll and triage would mean either fetching all
bodies upfront (wasteful) or building a two-file queue with deferred body fetches
(complex). The combined approach is simpler and correct.

An OAuth refresh token is stored in ~/.it-jobs/outlook-token.json. The script checks
expiry on every run and refreshes silently if the access token is within five minutes of
expiring. The refresh is written atomically (write to .tmp, then os.replace) so a crash
mid-write never corrupts the token file.


LLM Triage
----------

Both pipelines use the same two-stage pattern: a fast, cheap Flash model filters the
majority of posts, and only the ones that pass go to the more capable Pro model for a full
evaluation.

Stage 1 — Flash filter

@it_jobs_cyprus: The first 18 lines are sent in a single call. Flash returns is_vacancy
(distinguishes actual job offers from CVs and off-topic posts) and flag (is the role
relevant to the candidate profile). This is a deliberate batch because the first 18 lines
of a typical posting on this channel contain enough signal — role title, tech stack,
company type — to decide quickly.

@cyithr: Flash reads one line at a time, accumulating context, and at each step returns
irrelevant, relevant, or next. Reading stops the moment a decision can be made. This
strategy suits a noisier channel where the first line might be a logo or a decorative
emoji, and the relevant signal appears further down. Every single line step — including
intermediate next decisions — is written to the audit log so the full reasoning path is
visible per message.

Email: Flash sees only the From address and Subject line. This is the cheapest possible
filter: most irrelevant emails (PhD calls, faculty positions, off-geography roles) are
identifiable from the header alone without paying to fetch the body.

Stage 2 — Pro evaluation

When Flash flags a posting, the Pro model receives the full text alongside the detailed
candidate criteria file. It decides send or skip and, if sending, writes a 3-5 sentence
Telegram message covering role, company, tech stack, geography, salary if stated, and how
to apply. The delivered message is prefixed with the origin — @channel · @poster for
Telegram posts, subject · from for emails — so the source is always visible in chat.

All LLM decisions, including errors, are appended to a JSONL audit log. The decision field
uses distinct values (flag, skip, irrelevant, relevant, next, read, send, error) so
pipeline behavior can be reviewed and tuned per channel with simple jq queries. See
llm_audit.md for the full schema and example queries.


Tech Stack
----------

Layer                   Technology
-----                   ----------
Language                Python 3.10+ (stdlib only, except Telethon)
Telegram polling        Telethon — user-API client
LLM calls               DeepSeek API (deepseek-v4-flash, deepseek-v4-pro) via raw urllib
Email polling           Microsoft Graph API via raw urllib + OAuth2 refresh token
Delivery                Telegram Bot API via raw urllib
Scheduling              systemd user service + timer (Persistent=true, linger enabled)
Venv                    jobsmcp/ — isolated from system Python

No anthropic, no openai, no requests. The only third-party dependency is Telethon, which
is required for the Telegram user API — the bot API cannot read public groups as a user.


State directory: ~/.it-jobs/
-----------------------------

File                            Purpose
----                            -------
.env                            API keys and credentials
it-jobs-criteria.md             Candidate profile and triage rules for Telegram groups
email-triage-criteria.md        Candidate profile and triage rules for email
it-jobs-cursor                  Last seen message ID for @it_jobs_cyprus
cyithr-cursor                   Last seen message ID for @cyithr
email-cursor                    receivedDateTime of last processed email
it-jobs-session.session         Telethon session file (created once interactively)
outlook-token.json              Outlook access + refresh token (auto-refreshed)
message_queue/                  Transient post files — written by poller, deleted by triage
it-jobs-triage.jsonl            LLM audit log for Telegram pipelines
email-triage.jsonl              LLM audit log for email pipeline
it-jobs.log                     Operational log (stdout/stderr from systemd)


Scheduling
----------

A systemd timer fires the service at :15 past every even hour:

    0:15, 2:15, 4:15, ... 22:15

The service runs three ExecStart steps sequentially: poller, triage, email-triage.
Persistent=true means a missed firing (machine off or asleep) runs immediately on next
boot. loginctl Linger=yes ensures the user service starts on boot without requiring an
active login session.


Installation
------------

    git clone <repo> it-jobs
    cd it-jobs
    ./setup.sh

setup.sh creates the venv, installs Telethon, copies the criteria templates, writes an
empty ~/.it-jobs/.env, and generates the systemd service and timer files with the correct
absolute paths substituted in.

After setup:

1. Fill in ~/.it-jobs/.env:

       TELEGRAM_BOT_TOKEN=     # bot that delivers matches to your chat
       TELEGRAM_API_ID=        # from my.telegram.org
       TELEGRAM_API_HASH=      # from my.telegram.org
       DEEPSEEK_API_KEY=       # from platform.deepseek.com
       OUTLOOK_CLIENT_ID=      # Azure app registration client ID

2. On a new machine, copy outlook-token.json from the previous machine:

       scp old-host:~/.it-jobs/outlook-token.json ~/.it-jobs/
       chmod 600 ~/.it-jobs/outlook-token.json

   Re-doing the OAuth browser flow is the alternative if the token is unavailable.

3. Run the poller once interactively for the Telethon OTP login:

       jobsmcp/bin/python3 it-jobs-poller.py

   Follow the prompts (phone number + OTP). The session file is saved and reused
   automatically on all subsequent runs.

4. Start the timer:

       systemctl --user start it-jobs.timer
       systemctl --user status it-jobs.timer
